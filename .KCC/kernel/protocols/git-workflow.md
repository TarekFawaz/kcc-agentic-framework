# Git Workflow

How a KCC workspace uses branches, commits, pushes, and pull requests. The
rules are enforced by two tools and three git hooks, and configured in
`.KCC/settings.json -> git`. Without that section the tools use the built-in
defaults described here. [[repo-bootstrap]] settles the repo state first;
this protocol applies from the first commit after it.

## Model: trunk + spec branches

| Branch | Pattern | Created by | Lifetime | Merges into |
|--|--|--|--|--|
| Trunk | `main` (protected) | repo bootstrap | permanent | - |
| Spec | `spec/SPEC-{ID}` | implementer or repo-steward, from trunk | one spec | trunk, by pull request |
| Lane | `lane/SPEC-{ID}-w{N}` | repo-steward, from the spec branch | one parallel wave | its spec branch, locally |
| Bug | `bug/SPEC-{ID}-Bug-{NNN}` | repo-steward, from trunk or the spec branch | one bug item | the branch it came from (trunk only by pull request) |
| Chore | `chore/{slug}` | human or repo-steward, from trunk | one maintenance change | trunk, by pull request |

Rules:

- Work happens on a work branch, never on a protected branch.
- A spec branch is short-lived: it is opened when `/spec-implement` starts
  and closed by the pull request that follows an `APPROVED` `review.md`.
- Lane branches exist only when a wave runs with git-worktree isolation
  ([[parallel-execution]] -> *Optional: git-worktree isolation*). The default
  shared working tree needs no lanes. Lanes are merged into the spec branch
  at the wave barrier with `git merge --no-ff`. Waves are file-disjoint, so a
  conflict means the plan was wrong: abort the merge and report it.
- A change reaches a protected branch **only by pull request, after the
  verifier's `review.md` verdict is `APPROVED`**. The pull request is opened,
  approved, and merged by a human on the hosting platform.
  `/spec-merge SPEC-{ID}` prepares the draft and the commands.
- History that has been pushed is never rewritten.

## Commit messages

The subject line (first non-empty, non-comment line) has one of these forms:

| Form | Use |
|--|--|
| `SPEC-NNN (Story\|Enabler\|Bug)-NNN: subject` | Work on one backlog item. A Test ID may follow the item: `SPEC-003 Story-001 T-004: ...`. |
| `SPEC-NNN: subject` | Spec-level change (plan, review, docs of that spec). |
| `(chore\|docs\|ci\|build\|test\|refactor\|fix\|feat)(scope)?: subject` | Maintenance outside a spec. `!` before the colon marks a breaking change. |
| `Merge ...`, `Revert ...`, `fixup! ...`, `squash! ...`, `amend! ...` | Generated by git; always accepted. |

Further rules:

- One space after the colon; the subject is not empty.
- When the subject names a `SPEC-NNN` and `specs/` exists, the spec folder
  must exist; when it names an item, `Backlog/{Kind}-NNN-*.md` must exist in
  that spec. Without a `specs/` folder the reference is not verified (warning).
- Keep the subject at 72 characters or fewer (warning above that).
- One commit maps to one plan step or backlog item where practical.

Checked by `check-commit-msg`:

| ID | Severity | Meaning |
|--|--|--|
| `COMMIT-MSG-001` | error | Message is empty. |
| `COMMIT-MSG-002` | error | Subject does not match the convention (or `git.commit_pattern`). |
| `COMMIT-MSG-003` | error | `SPEC-NNN` has no spec folder under `specs/`. |
| `COMMIT-MSG-004` | error | The named Story/Enabler/Bug is not a backlog item of that spec. |
| `COMMIT-MSG-005` | warning | `specs/` is absent; the reference was not verified. |
| `COMMIT-MSG-006` | warning | Subject is longer than 72 characters. |

## Branch names and pushes

Checked by `check-branch`:

| ID | Severity | Meaning |
|--|--|--|
| `BRANCH-001` | error | Branch name matches no allowed pattern. |
| `BRANCH-002` | warning | The checked branch is a protected branch (name mode). |
| `BRANCH-003` | error | A push updates or deletes a protected branch directly. |
| `BRANCH-004` | warning | A push creates the protected branch on the remote (first publish of a new repo). Allowed once; later changes go by pull request. |
| `BRANCH-005` | warning | Detached HEAD; nothing to check. |

`check-branch` checks the current branch, or `-Branch <name>`. With `-Push`
it checks a push target instead: `-RemoteRef <ref>`, or the lines git gives a
pre-push hook on stdin (`<local ref> <local sha> <remote ref> <remote sha>`).
Tags and other non-branch refs are not checked.

## Push policy

KCC never pushes on its own. No agent, skill, or tool runs `git push`,
`git push --force`, a merge into a protected branch, or a history rewrite of
pushed commits. These are human actions. An agent that needs one prints the
exact command and stops. This matches [[repo-bootstrap]] -> *Push policy*.

The hooks below make the same rules hold for commands a human or a harness
runs by hand. Bypassing a hook (`--no-verify`) is an explicit human decision.

## Hooks

Sources live in `.KCC/tools/hooks/`. `repo-bootstrap -Apply init-local`
installs all three; `repo-bootstrap -InstallHook` installs or refreshes them
later. An existing foreign hook is kept as `<hook>.local` and runs first.

| Hook | Runs | Blocks when |
|--|--|--|
| `pre-commit` | `check-impl-lock --staged`, `quality-gate --fast` | the implementation lock is closed for a staged path, or a staged file holds a secret |
| `commit-msg` | `check-commit-msg --file <message file>` | the message breaks the convention |
| `pre-push` | `check-branch --push`, then `quality-gate` in the `git.pre_push_gate` mode | the push targets a protected branch, pushes a branch with a disallowed name, or the gate finds violations |

Exit handling is the same in every hook: a tool exit of `1` blocks; `3`
(deferred, a scanner is missing) warns and allows, and is not a pass; any
other failure warns loudly and allows.

## Configuration

`.KCC/settings.json`:

```json
"git": {
  "model": "trunk",
  "protected_branches": ["main"],
  "branch_patterns": {
    "spec": "spec/SPEC-{ID}",
    "lane": "lane/SPEC-{ID}-w{N}",
    "bug": "bug/SPEC-{ID}-Bug-{NNN}",
    "chore": "chore/{slug}"
  },
  "commit_pattern": null,
  "pre_push_gate": "fast"
}
```

| Key | Values | Default | Meaning |
|--|--|--|--|
| `model` | `trunk` \| `off` | `trunk` | `trunk` is the model above. `off` disables the branch-name and push-target checks (`check-branch` passes); commit-message checks still run. |
| `protected_branches` | array of names; `*` is a wildcard (`release/*`) | `["main"]` | Branches that take changes only by pull request. `[]` means none. |
| `branch_patterns` | object, label -> pattern | the four patterns above | Allowed work-branch names. When present it replaces the default set. Labels are free text. |
| `commit_pattern` | `null` \| regular expression | `null` | When set, replaces the three built-in subject forms. Write it in POSIX ERE that is also valid .NET regex (`[0-9]`, not `\d`). Git-generated subjects still pass, and `SPEC-NNN` references are still verified. |
| `pre_push_gate` | `fast` \| `full` \| `off` | `fast` | What `quality-gate` runs before a push: `fast` = secrets scan of the working tree (`--scope secrets`), `full` = the whole gate, `off` = nothing. |

Pattern tokens: `{ID}`, `{N}`, `{NNN}` match one or more digits; `{slug}`
matches letters, digits, `.`, `_`, `-`, `/` (starting with a letter or
digit); `*` matches anything. Every other character is literal. A pattern
must match the whole branch name.

Common adjustments:

- **Trunk is not called `main`:** set `protected_branches` to its name
  (for example `["master"]`), or rename the branch. A repository created by
  `repo-bootstrap -Apply init-local` starts on `main` even where git's own
  default is `master`.
- **No pull-request platform (local or single-developer repo):** set
  `protected_branches` to `[]` and add the trunk to `branch_patterns`
  (for example `"trunk": "main"`), or set `model` to `off`.
- **Additional branch families:** add entries to `branch_patterns`
  (for example `"release": "release/{slug}"`).

A missing `git` section, a missing key, or a `null` value means the default.
An unknown `model` is a usage error (exit `2`).

## Tools

Both follow [[../contracts/tool-contract|tool-contract]]: paired `.ps1` /
`.sh`, `-RepoRoot` / `--repo-root`, `-Json` / `--json`, exit `0` pass, `1`
violations, `2` usage. They are read-only and need no network.

```text
check-commit-msg (-File <path> | -Message <text>)
check-branch     [-Branch <name>]
check-branch     -Push [-RemoteRef <ref>]
```

## Roles

| Actor | Does | Never does |
|--|--|--|
| implementer | creates `spec/SPEC-{ID}` when it starts; commits in the convention | push, merge to a protected branch |
| repo-steward | creates and validates branches, checks commit hygiene, merges lanes into the spec branch, drafts the pull request, proposes tag and changelog entries | push, merge into a protected branch, force-push, rewrite pushed history |
| human | pushes, opens / approves / merges the pull request, tags releases | - |
